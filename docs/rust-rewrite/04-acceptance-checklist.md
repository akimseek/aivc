## PTY 泄漏的根因与修复（已完成）

### 症状

第一次真正运行 `cargo test -p aivc-terminal --features pty` 的**实测结果**：

- 测试挂住不返回（>3 分钟无输出，只能强杀）；
- 强杀后系统里留下 **20 个 `conhost.exe` + 3 个 `OpenConsole.exe`**；
- 这些残留进程让 DSH 的作业运行器无法「证明托管范围为空」，
  **整个会话卡死**（`subprocess-local: Windows Job runner exited with exit code 3221225794`）。

### 两个独立缺陷

**缺陷 1：`kill()` 之后没有 `wait()` 回收子进程。**

```rust
impl Drop for PtySession {
    fn drop(&mut self) {
        let _ = self.child.kill();   // ← 只 kill，没有 wait
        self.release();
    }
}
```

未回收的进程对象会让控制台宿主（`OpenConsole.exe` / `conhost.exe`）一直活着。

**缺陷 2：ConPTY 的 DSR 查询没人应答。**

`ConPTY` 启动后会发 `ESC[6n`（光标位置查询），**并在拿到应答前不推进会话**。
真实环境由 xterm.js 自动应答；测试里没有终端模拟器，于是只收到这一条查询、
看不到任何命令输出，而 `wait()` 就永久阻塞在那里。

### 修法

1. `kill()` 与 `Drop` 都补上 `child.wait()` 回收；
2. 测试侧像终端模拟器那样**应答 DSR**（`session.write("\x1b[1;1R")`）。

### 实测结果

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 单个用例 | 10.04s 超时失败 | **0.07s 通过** |
| 整套 63 项 | 挂死 >3 分钟 | **10.31s 全通过** |
| `conhost`/`OpenConsole` 增量 | **+23** | **0** |
| `cargo` 退出码 | — | **0** |

### 一条生产级约束（已写入代码注释）

**必须边排空输出边等待进程。** 阻塞等待进程结束而不排空输出会死锁：
读取线程往有界通道里写，通道满了就阻塞，`ConPTY` 的输出管道随之填满，
子进程再也推不动。这不只是测试的事——应用层同样必须并发地
「读输出 → 送渲染层 → 把渲染层的应答写回」。

### 教训

**「代码写了 + 编译过 + Lint 过」与「能运行」之间隔着一整类缺陷。**

I1 此前被标为 🔶（待核对）而非 ❌，正因为我没有把「未运行」当成「未实现」。
实测证明它当时连**最基本的不泄漏**都做不到。

反过来，**修好之后的收益也是成倍的**：`pty` 特性现在**默认开启**，
这 63 项测试进入常规门禁——它们验证的正是「终端真的能跑」，
而这恰恰是最需要持续验证的一件事。
