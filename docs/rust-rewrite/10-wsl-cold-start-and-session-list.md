# 10 · 「会话列表打不开」的根因：WSL 冷启动，不是协议

> 用户反馈：「无法进入会话，这就很严重了」。
>
> 根因已定位并修复：**WSL2 会在空闲后自动关闭发行版**，而列表读取每个文件发一次
> `wsl.exe`、配 6 路并发，于是 6 个进程去抢同一次冷启动。
>
> 实测改善：**30.5 秒 → 0.416 秒**（14 条会话）。

---

## 1. 证据：应用日志的时间线

`target\debug\logs\app.log`（用户 16:25 那次运行）：

```
16:25:38.464536  codex:list-sessions        ← 用户点开目标
16:25:38.465594  WSL exists 脚本(123 B)
16:25:46.872821  WSL find  脚本(159 B)      ← 空了 8.41 秒
16:25:47.075905  WSL head(203 B)            ← 0.20 秒
16:25:47.086484  head                        ← 0.011 秒
16:25:47.093547  head                        ← 0.007 秒
16:25:47.101299  head                        ← 0.008 秒
16:25:47.110419  head                        ← 0.009 秒
16:25:47.118823  head                        ← 0.008 秒   ← 到此是一整波（6 路并发）
16:25:47.205369  head                        ← 0.087 秒
16:25:47.217328  head                        ← 0.012 秒
16:26:17.204255  head                        ← **空了 29.99 秒**
16:26:17.210187  head
16:26:17.216882  head
16:26:17.222996  head
16:26:18.936556  退出清理                    ← 用户等不下去，关掉了应用
```

读法：`执行 WSL 脚本` 这行日志打在调用**开始时**，所以「两行之间 29.99 秒的空白」
意味着**前一个 `head` 卡了 30 秒**。

那 6 行间隔 7–11 ms 的 `head` 是**同一波并发**（`LIST_PARSE_CONCURRENCY = 6`）。

**用户看到的就是这个**：会话列表转 30 秒不动，关掉应用。

---

## 2. 实测：冷启动的真实代价

在目标发行版上直接计时（权限放宽后）：

| 场景 | 耗时 |
| --- | --- |
| 发行版 `Stopped` 时首次调用 | **5267 ms** |
| 紧接着调用 | **94 ms** |
| **空闲 20 秒后** | **6897 ms** |

`wsl -l -v` 的旁证：三个发行版全部 `Stopped`，而 `vmmemWSL` 仍占 1146 MB。
**WSL2 会在空闲后自动关掉发行版**（约 20 秒），下一次调用必须冷启动。

回答用户的问题「老平台加载挺丝滑，不清楚怎么加载的」：**它面对的是同一套 WSL 行为**，
差别只在调用的**节奏**——一批紧挨着的调用只需付一次冷启动；被应用侧处理（解析、写库、
前端往返）拉开的调用要反复付。这一条我**没有实测对比老平台**，因此只是解释，不是结论。

---

## 3. 被推翻的假设：登录 shell

我上一轮记录过一个假设：原平台用直接执行（`wsl.exe -d X -- head ...`），
我用登录 shell（`bash -lc "printf <b64> | base64 -d | bash"`），因此慢。

**实测推翻了它**——14 个文件、两种方式，逐个计时：

| 方式 | 单次耗时 |
| --- | --- |
| 直接执行 | 92–121 ms |
| 登录 shell + base64 | 87–104 ms |

**两者没有差别。** 假设是错的，没有当成结论写进代码。这也说明：
**测量和猜测的结论经常不一样**，而这次差得很远。

---

## 4. 修复：一次调用读一批

- `SessionStore::read_heads`（`aivc-core/src/ports.rs`）——新增，带默认实现（逐个读）。
- `WslSessionStore::read_heads`——**覆盖**为一次 `wsl.exe` 调用。
- `WslAdapter::read_heads`——按 `HEAD_BATCH_SIZE = 40` **分批、串行**发起。
- `list_sessions_from_files`——先做缓存命中判定，未命中的**一次批量读**。

脚本里路径以 base64 逐行写进引号 heredoc（`<<'AIVC_PATHS'`），**完全不经过 shell 解析**，
因此含空格、引号、`$`、换行的路径都不会破坏脚本。

输出每行 `ok <base64>` 或 `missing`：用前缀而不是「空行即失败」，是为了把
**存在但为空**的文件与**不存在**区分开。解析时输出行数不足**补 `None`** 而不是截断——
调用方按下标把内容与文件元数据对齐，**错位比缺失危险得多**。

14 个文件从 14 次调用（3 波并发）压成 1 次。

## 6. 两次「假绿」的教训

这个测试两次「通过」都是假的：

1. **第一次**（0.06 秒）：沙箱拒绝 `wsl.exe`，辅助函数用 `Option` 把「无法取得基准」
   和「本机没有 WSL」合并成同一个 `None`。已改为 `Result<_, String>`，
   跳过时必须打印 `⚠ 跳过：<原因>——本用例没有验证任何东西。`
2. **第二次**（405 µs）：目标列表改为列出全部发行版后，测试取「第一个 WSL 目标」，
   恰好取到**进不去**的 `Ubuntu-22.04`，它走空 `codex_home` 的 guard 直接返回。
   已改为**按 `available` 过滤**并要求至少测到一个。

**假绿比红灯危险**：红灯会有人去修，假绿只会让人以为已经测过了。

## 7. 关于「目标列表要几秒」——缓存其实已经在工作

同一次运行的 `performance.log`：

```
16:25:17.620  ui.listCachedTargets   ok [2]   durationMs 7     ← 7 毫秒，读缓存
16:25:19.398  ui.listTargets         ok [3]   durationMs 274   ← 1500 ms 后刷新
```

所以：

- **缓存路径是快的**（7 ms），首屏立刻有目标；
- 用户看到的「几秒后刷新出来」，是因为**缓存里是旧的 2 个**（修复前写入的），
  而新探测到 3 个——列表**可见地变了一下**；
- 现在缓存里有 3 个，下次启动首屏就是完整的。

这是原平台的设计（先渲染缓存、1.5 秒后再刷新），保持不变。

**仍然可以改进的一点**：`providerId` 初始为空，用户每次都要**手动选一次平台**
（日志里 `listProviders` 在 16:25:14，`listCachedTargets` 在 17.615，中间 3.5 秒
是人在操作）。把「上次用的平台与目标」持久化并在启动时恢复，可以省掉这一次点击。
**这一条我还没有做**，因为它改变启动行为，想先确认。

## 8. 仍未解决：常驻 worker 是真正的根治

批量读取把「反复抢冷启动」消掉了，但**单次冷启动的 5–7 秒仍在**。

根治办法是让发行版**不进入空闲**——即一个常驻进程，也就是这个工程里已经存在但
**当前被关闭**的 WSL worker（`WslConfig { use_worker: false }`）。

它当初被关掉是因为**它自己有病**（实测探测耗时 198 秒，一个发行版退出、另一个挂住）。
修好它才能把这 5–7 秒也去掉。

**状态：未修，只是被绕过。** 这是「会话列表」这条链上剩下的最后一段。
