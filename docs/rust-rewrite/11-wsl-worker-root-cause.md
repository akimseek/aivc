# 11 · 常驻 worker 为什么从来没能工作过

> 承接 [10](10-wsl-cold-start-and-session-list.md)：批量读取消掉了「反复抢冷启动」，
> 但单次冷启动的 5–7 秒还在。根治办法是让发行版**不进入空闲**，也就是常驻 worker。
>
> 结论：worker **在生产里从来没有工作过**，原因是两个叠加的缺陷，而两个都因为
> 「测试替身与生产实现不一致」而完全不可见。

---

## 1. 修复前：worker 一启动就退出

打开 `use_worker` 后立刻复现：

```
WARN aivc_infra::wsl::adapter: WSL worker 调用失败，回退到一次性执行
    distro="Ubuntu-24.04" operation="exists"
    error=WSL 持久 worker 协议异常：worker 已退出（Ubuntu-24.04）
```

每一次调用都退回一次性执行——**比不开 worker 还慢**，因为多付一次注定失败的启动。

---

## 2. 缺陷 A：一个方法承担了两种相反的 stdin 契约

`WslWorker::spawn` 调用 `launcher.spawn_bash()`，然后要求 `child.stdin` 存在。
而生产实现 `WslExeLauncher::spawn_bash` 把 stdin 设成了 `Stdio::null()`——
那是为了修一次性路径上「命令误读 stdin 导致 30 秒阻塞」而做的。

两种需求正好相反，却共用了一个方法。trait 上的文档甚至写着「实现必须把
stdin/stdout/stderr 都设为 `piped`」——**文档与生产实现相互矛盾**，而矛盾本身就是缺陷。

**修法**：拆成两个方法，契约写进名字和文档。

| 方法 | stdin | 用途 |
| --- | --- | --- |
| `spawn_bash` | `null` | 一次性脚本 |
| `spawn_bash_interactive` | 管道 | 常驻 worker 的帧协议通道 |

---

## 3. 缺陷 B：传输形状把 worker 的 stdin 吃掉了

修完 A 之后 worker **仍然**立刻退出。真正的根因在传输层：

```text
printf %s '<base64>' | base64 -d | bash
```

脚本是**从 stdin 读进去**的。对一次性执行没问题，但 **worker 的 stdin 就是帧协议
通道**——bash 先把它读干当脚本来源，于是 worker 的 `while read` 第一轮就撞上 EOF，
进程立刻退出。

### 实测过的四种形状

| 形状 | 参数里有双引号 | 脚本原样 | stdin 完好 | 结果 |
| --- | --- | --- | --- | --- |
| `printf %s '<b64>' \| base64 -d \| bash` | 否 | ✅ | ❌ **被吃** | 脚本跑了，但读不到 stdin |
| `eval "$(printf %s '<b64>' \| base64 -d)"` | 是 | ✅ | ✅ | ❌ **输出为空，整个失效** |
| `eval $(printf %s '<b64>' \| base64 -d)` | 否 | ❌ **词分割** | ✅ | 脚本里的 `#` 注释会注释掉后续全部内容 |
| **`source <(printf %s '<b64>' \| base64 -d)`** | 否 | ✅ | ✅ | ✅ **采用** |

双引号穿不过 `Windows 命令行 → wsl.exe → bash` 这三层解析——这一点是**跑出来的**，
不是推断的。而未加引号的命令替换会做词分割，把脚本里的 `#` 注释变成「注释掉后面所有
行」：实测脚本 `# a comment\nprintf 'A:%s\n' 'spaced'` 在第三种形状下行为已经错乱。

**修法**：新增 `wrap_script_preserving_stdin`，形状为
`source <(printf %s '<载荷>' | base64 -d)`——参数里没有双引号，脚本以**文件**形式
交给 `source`，既不做词分割、也不碰 stdin。

---

## 4. 为什么测试一直看不见

**同一个模式咬了两次：测试替身与生产实现在关键行为上不一致。**

| | 测试替身 `LocalBashLauncher` | 生产 `WslExeLauncher` |
| --- | --- | --- |
| 缺陷 A 时的 stdin | `piped` ✅ | `null` ❌ |
| 缺陷 B 时的传输 | 直接 `bash -lc <script>`（不吃 stdin）✅ | 管道形状（吃掉 stdin）❌ |

worker 的测试全部通过，因为它们用的是替身；而**替身恰好把生产实现搞错的那两件事都做对
了**。现在两个实现共用同一份契约与同一组形状选择，缺陷不会再有藏身之处。

另外：这 48 项 worker 测试在受限沙箱里**全部被跳过**（MSYS2 bash 无法创建内部
signal pipe），因此连「测试通过」都是空的。放宽权限后实测 **18 项**真的跑了。

---

## 5. 效果

新增的守门测试（`the_persistent_worker_keeps_the_distro_warm_across_an_idle_gap`）
在空闲 25 秒前后各列一次会话：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 首次列出 | 994 ms | 224 ms |
| **空闲 25 秒后** | **3.88 s**（冷启动） | **22.9 ms** |
| 发行版状态 | 需要重启 | **Running** |

**冷启动消失了。** 空闲 25 秒后仍是 22.9 毫秒，因为 worker 是一个活着的进程，
WSL 不会关闭它。

---

## 6. 顺带修的三处

1. **worker 失败冷却**（`should_try` + `WORKER_FAILURE_COOLDOWN = 60s`）。
   worker 失败后曾在下一次调用立刻重建，于是**每次操作都先付一次注定失败的启动**。
   实测：本机有一个发行版注册在册却进不去（VHDX 挂载被拒），一次目标探测因此从数秒
   涨到 **19 秒**。冷却期内安静地走一次性路径，既不重复失败启动，也不每次刷告警。

2. **门禁不再吞掉失败详情**。`verify.ps1` 只回显以 `error`/`warning` 开头的行，
   而 Rust 测试失败的详情以 `failures:` / `---- <用例名> stdout ----` 开头，
   **断言消息**在 `panicked at` 那一行。整个被吞掉的结果是只能看到一个光秃秃的
   `exit 101`——而偶发失败未必跑得出来。已加入这三个模式。

3. **`verify.ps1` 的 UTF-8 BOM**。编辑工具写文件时不带 BOM，而这台机器上的
   PowerShell 会按 GBK 解读没有 BOM 的脚本，于是中文注释变成乱码、`$PSScriptRoot`
   变成 null，脚本直接崩。**改完 `.ps1` 必须补回 BOM。**（已修复，并记录在此。）

4. **这个文件里的 WSL 用例改为串行**。它们共用同一个外部资源，并行跑会互相争抢：
   单独 32 秒的文件在全量门禁里变成 91 秒，并导致上面那条守门测试**偶发失败**。
   诊断性集成用例串行化是正确取舍——宁可慢，也不要一个会随机变红的门禁。

---

## 7. 已完成：批量读头也走 worker

`WorkerOp::ReadHeads` 新增之后，列表路径的批量读头不再启动 `wsl.exe`，只走一次管道
往返。回退路径与 worker 路径**共用同一个脚本**（`read_heads_script`）——两条路必须产出
同一种输出，否则「同一批文件走哪条路」会给出不同结果，那是最难查的一类差异。

实测「列出 WSL 会话（14 条）」的演进：

| 阶段 | 耗时 |
| --- | --- |
| 最初（每文件一次 `wsl.exe`、6 路并发） | **30.5 s** |
| 批量读（一次 `wsl.exe`） | 337 ms |
| 批量读走 worker | **165 ms** |

## 8. 启动预热收窄（只预热主平台）

### 原来错在哪

`App::start` 无条件探测**全部 4 个平台 × 2 个发行版**。实测日志：

```
目标预热完成 count=8 elapsed_ms=3681
```

21 次 `wsl.exe` 调用，2888–3681 毫秒，**而且和界面自己的首次探测抢同一个发行版**——
本该加速首屏的东西反而拖慢了它。

### 关键判断：预热真正不可替代的作用只有一个

**让发行版热起来**（WSL2 空闲约 20 秒就关掉它，冷启动 5–7 秒）。

目标缓存**不需要预热代劳**——用户选中平台后，界面一定会调一次 `codex:list-targets`，
那一次就会把缓存刷新。预热去填缓存是重复劳动。

### 改法

| 情况 | 行为 |
| --- | --- |
| **有缓存**（后续启动） | 只按缓存里的可达 WSL 目标温热 worker，一个目标**一次**廉价探测 |
| **没缓存**（首次启动） | 才做完整探测，而且**只探主平台**（Codex） |

其余平台在用户切过去时按需探测——那一次探测本来就要付，提前付只是把它变成
**每一个用户都为用不到的平台各付一遍**。

预热同时抽成了独立的 `App::warm_targets`：一是 `App::start` 要表达的是**装配顺序**，
预热不属于那里（抽出来之前它把 `start` 顶到了 153 行，越过 clippy 的 150 行上限）；
二是后台任务里的东西测试等不到，抽出来之后测试可以直接 `await`。

### 实测

| | 旧 | 新·首次启动 | 新·后续启动 |
| --- | --- | --- | --- |
| 预热探测的平台 | 4 | 1 | 1 |
| `wsl.exe` 调用次数 | ~21 | 3 | **1** |
| 预热耗时 | 3681 ms | 3338 ms | **106 ms** |
| 目标数 | 8 | 3 | 3 |
| 启动日志行数 | 36 | 21 | **15** |

后续启动那 106 毫秒只做一件事：建常驻 worker。**首屏不再被预热抢占**——实测界面在
启动后 **553 毫秒**就发出了第一批命令，而预热还在后台冷启动发行版。

首次启动那 3.3 秒是**发行版冷启动本身**（不可省，且已被挪到后台）。

## 10. 顺带发现：新旧两个应用共用同一个 `settings.json`

跑真实可执行文件时发现，Rust 应用与旧 Electron 应用**写同一个设置文件**
（`<运行根>/data/user-data/settings.json`），其中的 `cachedTargets` 会互相覆盖。

实测到的样子：文件里同时有我的目标（`WSL · Ubuntu-24.04`，带 `available: false` 语义）
和旧应用的目标（`Gemini：WSL：Ubuntu-24.04`，旧标签格式）——因为 `merge_cached_targets`
按平台覆盖，只替换 `codex` 那几条。

**数据文件名是刻意与旧工程区分的**（`aivc.db`，见 `database_file_name_differs_from_the_legacy_project`
测试），设置文件却没有区分。这可能是疏漏，也可能是**有意保留**——用户偏好（网关端口、
供应商、WSL 目录覆盖）本来就该沿用。

但 `cachedTargets` 是**派生数据**，且两边的标签与语义不同，共用它会互相污染：
谁的标签出现在对方的界面上，取决于谁最后写。

**这是一个设计决策点，我没有擅自改。** 可选做法：

1. 设置文件也区分（`aivc-settings.json`）——最干净，但用户偏好不再沿用；
2. 只把 `cachedTargets` 换个键名（如 `aivcCachedTargets`）——保留偏好、隔离派生数据；
3. 维持现状——只在用户同时运行两个应用时才有影响。
