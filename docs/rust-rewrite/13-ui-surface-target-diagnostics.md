# 13 · UI 第 1 轮：把目标的四态诊断送到用户眼前

> 后端为每个目标算出了**四态** `detail`（见 [09](09-target-list-diff-vs-legacy.md)）：
>
> | 状态 | `available` | `detail` |
> | --- | --- | --- |
> | 找到 `sessions` | `true` | `找到 Codex 会话` |
> | 有配置目录、无 `sessions` | `true` | `找到 Codex 目录` |
> | 进得去、无 Codex | `true` | `可进入 WSL，未找到 Codex 目录` |
> | **进不去** | **`false`** | `无法进入 WSL：<原因>` |
>
> 这一轮解决的是：**这些信息此前几乎到不了用户眼前。**

---

## 1. 先盘点，别猜

我一开始以为「`detail` 只在全局搜索的 tooltip 里用了一下」。**实际查过之后要更正**：

`provider-status-dialog.tsx` 里**已经有**一行 `{ label: "探测结果", value: target?.detail || "-" }`。
所以四态在**平台状态对话框**里是能看到的。

真正的问题是它在**主界面**上完全不可见——而用户遇到问题时看的是主界面，不是那个对话框。

## 2. 一处货真价实的误导

同一个对话框里：

```tsx
{ label: "命令状态", value: target.available ? "可用" : "未找到命令" }
```

**把所有「不可用」都说成「未找到命令」。** 而 WSL 目标不可用的原因几乎总是
**发行版进不去**（VHDX 挂载被拒、发行版未初始化），与「命令没装」完全是两回事。

把它们说成同一句话，会让用户去查一个不存在的问题——而真正的原因就在**下一行**
「探测结果」里。已按目标类型区分：

| 情况 | 文案 |
| --- | --- |
| 可用 | `可用` |
| 不可用 + WSL | `无法进入发行版` |
| 不可用 + 本机 | `未找到命令` |

## 3. 三处改动

### 目标选择器

- 不可用的目标**在列表里就标出来**（`（不可用）`）——等选中了才发现，用户已经先点了一次；
- 选中目标后，在下面显示它的 `detail`（带 `title`，截断时鼠标悬停可看全）。

用的正是**已经存在但从未被使用**的 `.target-detail` 样式（见 §4）。

### 会话区空状态

此前只有一句「未找到会话。」，于是三种完全不同的处境长得一模一样：

| 处境 | 改后 |
| --- | --- |
| 没选目标 | `请先在上面选择目标。` |
| 目标进不去 | `无法进入 WSL：<原因>`（来自 `detail`） |
| 目标能用、确实没会话 | `未找到会话。` |

用户对着同一句话却要做三件不同的事——这就是「空状态要能指导行动」的具体含义。

### 平台状态对话框

见 §2。

## 4. 顺带发现：又一个「设计了但从未接上」

`.target-detail` / `.target-detail small` 在 `app.css` 里定义得完完整整
（flex 布局、`text-overflow: ellipsis`、`white-space: nowrap`），**但没有任何使用者**。

这和上一轮删掉的 `AppPaths::user_data_dir()` 是同一类东西：**结构先行、接线缺失**。
区别是那个会让人误以为约束成立，而这个只是白写了一段样式——因此这一轮把它用上了，
而不是再写一份。
