# 14 · UI 第 2 轮：失败要带出口

> 第 1 轮把「为什么」送到了用户眼前（目标的四态 `detail`）。这一轮解决「**接下来做什么**」。

---

## 1. 先盘点：`checkCliEnvironment` 其实已经接了

计划里写的是「把 `checkCliEnvironment` 接起来」。查过之后要更正：

- 后端返回的 `CliEnvironmentStatus` **已经带 `messages: string[]`**（可执行建议），
  能区分 Node / npm / nvm / CLI 各自的缺失；
- 前端 `use-cli-installer.ts` **已经在调它**，`cli-installer-dialog` 也已经在展示。

**真正缺的不是「接上检测」，而是「失败现场没有入口」**：这些信息只存在于一个用户得
主动打开的对话框里。用户看到的是会话区一句「未找到会话。」，然后就没有然后了。

## 2. 三处改动

### 目标不可用时，在列表上方给出原因 + 出口

新增 `TargetProblemNotice`：显示 `detail`（第 1 轮的成果），并给出**两个真实存在的恢复路径**：

| 出口 | 走的路 |
| --- | --- |
| **重新探测** | `refreshProviderTargets()`——WSL 刚被关掉、发行版正在启动这类**暂时性**失败，重试一次就好 |
| **手动指定目录**（WSL 目标） | 打开会话设置。这是发行版进不去时**唯一**还能走的路（见 [09](09-target-list-diff-vs-legacy.md)）——而它此前只藏在菜单里 |
| **安装 CLI**（本机目标） | 打开安装对话框，它内部用 `checkCliEnvironment` 判断「能不能装、要不要先装 Node」 |

### 错误横幅带上「重试」

此前只有一句红字，用户唯一能做的就是猜。现在右侧有「重试」，它**强制重载会话**
（`loadSessions(targetId, view, true)`，跳过「已加载过就不重复加载」的短路）。

绝大多数失败是暂时的（WSL 冷启动、发行版刚被关掉），重试一次就能过——但界面上
此前没有任何地方告诉用户可以重试。

## 3. 一个刻意的设计决定：按**目标类型**判断，不按错误文本

「该给哪个出口」由 `target.kind` 决定，而不是去解析错误字符串。

**解析错误文本来猜「该做什么」是脆的**：后端换一句措辞，引导就会失效，而且是静默失效
——按钮还在，只是指向了错误的动作。而「WSL 目标 / 本机目标」是稳定的结构信息。

判断错了的代价不对称：把 WSL 的恢复路径给成「安装 CLI」，用户会走进一条**走不通的路**
（发行版都进不去，谈何在里面装东西）。

## 4. 可测性

本工程没有 jsdom，组件渲染测不了。因此把**唯一的分支**抽成纯函数
`targetProblemAction(target)`，并加了 3 条测试：

- WSL → `configure-directory`
- 本机 → `install-cli`
- **每个动作都有文案**——少一个会在界面上渲染成 `undefined`，那比没有按钮更糟

这是本工程既有的做法（`mergeKnownTarget` 也是这么处理的）。

## 5. 验证

| 项 | 结果 |
| --- | --- |
| `tsc --noEmit` | 通过 |
| `eslint src/renderer/src --max-warnings 0` | 通过 |
| 渲染层测试 | **20 个文件 / 91 项全过**（新增 3 项） |
| 产物 | `手动指定目录` / `安装 CLI` / `重新探测` / `此目标当前不可用` 都在 `index-Bfv7yOgF.js` 里 |
| 真实应用 | `renderer.mounted` 正常、目标探测 `count=3` |

**仍然没有肉眼看过界面。** 以上证明「代码能跑、改动进了产物、渲染层能挂载」，
不证明它**看起来对**。尤其需要真机确认的：目标不可用通知会不会和空状态**重复说同一句话**
（通知显示 `detail`，空状态在不可用时也显示 `detail`）——这是一个已知的观感问题，
我倾向于「通知在、空状态就该退回一句中性文案」，但那要看过才知道。
