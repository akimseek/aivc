# 17 · 组件层与内嵌终端

> （用户明确要求：能封装的必须封装，风格才统一），**以及内嵌终端**。

## 1. 组件层：为什么必须先做

界面写到第三个页面时，按钮的圆角、输入框的边框、空状态的留白已经开始各不相同——
每一个新页面都在「参照上一个页面」重写一遍样式。组件层就是终止这个过程。

**样式分三层，同一件事不在两处定义：**

| 文件 | 放什么 |
| --- | --- |
| `styles/tokens.css` | 设计令牌（配色、圆角、字号）。**被组件层与应用层共用**，因此单独成文件 |
| `components/components.css` | 基础控件：按钮、下拉、搜索框、分段切换、空状态、告警条、标签 |
| `app/app.css` | 只放布局与功能区 |

令牌单独成文件是有原因的：放在任一侧，另一侧就变成「引用别人的私有变量」。

**已有的组件：**

| 组件 | 封装的判断 |
| --- | --- |
| `Button` | `variant`（default/primary/**danger**）+ `small`。危险动作必须与普通动作视觉上分开——那一下会把文件移走或删掉 |
| `ChipGroup` | 活跃/回收站这类分段切换 |
| `Field` / `Select` / `TextInput` | 用 `<label>` 包住控件，点标签即聚焦（手写很容易漏） |
| `SearchInput` | 带 `busy` 态——后端搜索第二段**会扫全文**，慢到必须让用户知道「它在找」 |
| `EmptyState` | `message` 必须说清**是哪一种空** |
| `Notice` | **`actions` 是必需的**，不是可选的：没有动作的告警等于把问题丢回给用户 |
| `Tabs` | 会话与终端**共用一条标签条**——它们都是「我正在看的东西」 |
| `StatusPill` `Toolbar` `ToolbarSpacer` | 小组件，但消除的是最容易写歪的那几行 |

## 2. 内嵌终端

### 三件必须接对的事

1. **输入要回到 PTY**：`term.onData` → `terminal:write`。交互式程序会发 `ESC[6n`
   之类的查询，xterm 通过**同一个回调**给出应答。这条链路断了，界面显示正常但完全
   没反应——这正是后端注释里点名的「终端能动的关键一环」。
2. **输出是原始字节**：事件载荷是数字数组，直接 `term.write(Uint8Array)`，
   **不要先转字符串**——光标控制序列不是合法 UTF-8，转一次就废了。
3. **尺寸要告诉后端**：容器变化时 `fit()` 之后必须发 `terminal:resize`，
   否则 PTY 里的程序仍按旧尺寸排版，换行位置全错。

### 两个刻意的设计决定

**所有终端保持挂载，非前台的只隐藏。** 卸载会让 PTY 的输出无人接收而**丢失**——
用户切回来会发现中间断了一截。用 `visibility: hidden` 而不是 `display: none`：
后者会让容器尺寸归零，xterm 量不到尺寸，切回来排版是错的。

**事件只订阅一次，按 `terminalId` 分发。** 每个终端各自订阅一次也能work，但监听数会
随终端数增长，而且关闭时漏掉一个就留下一个永不触发的监听。

### 退出不等于关闭

收到 `terminal:exit` 只把标签标记为已退出，**不自动关闭**——自动关闭会让用户来不及看
最后几行输出，而那几行往往正是失败原因。

## 3. 验证

| 项 | 结果 |
| --- | --- |
| `tsc --noEmit` | 通过 |
| `vitest run` | 8 项通过 |
| `vite build` | **572.9 KB**（gzip 160 KB） |
| 真实应用 | 命令序列正常 |

**诚实说明：我没有点过终端。** 上面证明的是「类型正确、构建成功、应用能跑」。
终端的启动、输入、尺寸同步、退出都需要你在真机上验证。

## 4. 一个新出现的问题：产物从 235 KB 涨到 573 KB

xterm 被打进了主包。它只在用户**打开终端**时才需要，因此正确做法是按需加载
（`import()` 动态引入 `TerminalPane`），让首屏不必为终端付出代价。

本地加载 573 KB 并不慢，所以这不是紧急问题，但**应该做**——它正好是「首屏只加载首屏
需要的东西」这条原则的实例。
