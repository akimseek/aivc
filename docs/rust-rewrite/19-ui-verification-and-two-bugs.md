# 19 · 界面验证流程，与它第一次就抓到的两个问题

> 承接 [18](18-frontend-feature-completion.md)。这一轮把「看一眼界面」变成可重复的动作，
> 然后立刻用它抓到了两个此前不可能发现的问题。

---

## 1. 为什么需要这个流程

`cargo test`、类型检查、七项门禁能证明「类型对、逻辑对、能跑」。它们**看不见界面**。

而有一类问题只在界面上暴露：标题不可辨认、数字与实际不符、排版错位、元素被遮挡。
这类问题此前一直靠人肉发现 —— 所以第 15 到 18 轮里我反复写着同一句话：

> 诚实说明：我没有点过终端 / 没有肉眼看过界面。

**那句话本身就是流程缺失的症状。**

## 2. 做法

这是一个 Tauri + WebView2 应用，内核是 Chromium，因此支持**远程调试协议（CDP）**。

```
应用以 WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222 启动
  ↓
scripts/cdp-shot.cjs 连上 CDP（Node 24 自带 WebSocket，零依赖）
  ↓
Runtime.evaluate     → 点按钮 / 填表单 / 读 DOM（= 模拟操作）
Page.captureScreenshot → 离屏渲染出 PNG
  ↓
一张能看的图
```

```
./scripts/ui-check.ps1 -Name 02-基线 -Probe 'document.querySelectorAll(".row").length'
```

### 关键取舍

**用 CDP 而不是截屏。** `Page.captureScreenshot` 是**离屏渲染**：不依赖窗口可见、不会被
其它窗口遮挡。截屏在没有交互式桌面的环境里会拍到黑屏。

**调试端口是验证专用的**，绝不能进发布配置。

### 两个已知限制

1. **原生对话框拍不到**：文件选择框、系统通知是操作系统的真窗口，不在 WebView 里。
   涉及它们的路径（导出「另存到…」、技能导入）仍然只能手动验。
2. **不是 OS 级输入**：是 Chromium 的自动化协议（Playwright 的底层机制）。
   界面层面等价，抓不到真实鼠标轨迹这类东西。

### 踩过的两个坑（已修进脚本）

- **PowerShell 会吃掉表达式里的双引号**：`querySelectorAll(".row")` 变成
  `querySelectorAll(.row)`，报 `SyntaxError: Unexpected token '.'`。修法是表达式改从
  环境变量 `CDP_PROBE` 取。
- **脚本原本不打印求值异常**：抛错时 `value` 也是 `undefined`，与「求值成功但结果为空」
  长得一模一样，排查白费了两轮。现在显式输出 `exceptionDetails`。

## 3. 它第一次就抓到了两个问题

两个都是 `tsc`、12 项测试、七项门禁**都不可能发现**的。

### ① 会话标题全是 UUID

```
titles: ["98895b66-4bbd-4f62-9...", "01a0c2fc-4538-7d01-8...", ...]
tabs:   ["98895b66-4bbd-4f62-9..."]
```

列表 5 条的标题、标签页**全都是会话编号**。会话列表的唯一目的就是让用户认出
「哪条是我要的」—— 现在它不提供任何区分信息。

**根因**（`crates/aivc-provider/src/codex/parser.rs`）：

| 位置 | 事实 |
| --- | --- |
| `parser.rs:189-193` | List 模式只保留**前 8 条**消息（`LIST_PREVIEW_LIMIT`） |
| `parser.rs:207-211` | 标题从**这个预览缓冲**里找第一条合格的 user 消息，找不到就回退成编号 |
| `parser.rs:300-302` | `is_title_candidate` 会拒绝合成块（正确） |

Codex 会话文件的第一条 user 消息常常是系统注入的 `<multi_agent_mode>` 块，被正确拒绝；
而真正的用户提示词在**头部窗口之外**，于是全部回退成了编号。

**问题的本质**：标题查找被**预览缓冲的上限**绑住了。这两件事没有关系 ——
预览要限长是为了省内存，而找标题只需要扫描，不需要保留。

### ② `message_count` 被当成总数显示

```
headMeta: "2 条"      ← 界面显示
bubbles:  80          ← 实际渲染
hasEarlier: true      ← 还有更早的
```

侧栏每行也标着「2 条」「3 条」。

**根因**：`parser.rs:233` 把 `self.message_count` 当作会话的条数，但 List 模式只解析
了**文件头部 64 KB**，所以它是**头部窗口内的条数**，不是总数。
（`parser.rs:625` 那条 `计数必须是全量` 的断言是 Full 模式的。）

**问题的本质**：List 模式**不知道**总数，却把局部计数当成总数暴露出去。
界面上写「2 条」，用户理解的是「这个会话有 2 条消息」—— 这是**错误的陈述**。

## 4. 建议的修法（尚未实施）

**① 解耦「预览上限」与「标题查找」**

标题扫描独立于预览缓冲：遇到合格候选就记下，**不占用**那 8 条的名额。头部读完仍没有
合格候选时才回退编号。代价是 List 模式多留一个 `String`。

**② List 模式不要声称知道总数**

`message_count` 在 List 模式下应当**缺省**（而不是给一个局部值），界面只在 Full 解析
后显示条数，否则显示「—」或「已载入 N 条」。让界面说「不知道」永远好过说错。

这两条都要动 `Session` 的语义与前端展示，属于**跨层改动** —— 需要连着类型、测试与
界面一起改，不能只改一半。

## 6. ① 的修复：正确，但**不够**

按上面的分析把「标题查找」从预览缓冲里拆了出来（`parser.rs` 新增 `title_candidate`
字段，扫描独立于 `LIST_PREVIEW_LIMIT`），并加了回归测试。
**测试在旧行为下确实失败**（`left: "s1"` vs `right: "把登录改成 SSO"`）——不是假绿。

但截图验证显示：**列表里的标题仍然是 UUID**。

原因是真正的限制因素不是 8 条预览上限，而是**读取窗口本身**：

```
listing.rs:44   pub const LIST_HEAD_BYTES: usize = 64 * 1024;
```

这 5 个会话文件的前 64 KB 里**没有任何合格的 user 消息** —— 全是合成块。
没有候选可找，修复自然无从生效。

**这正是新增截图步骤的价值**：只看测试的话，我会报告「已修复」。
