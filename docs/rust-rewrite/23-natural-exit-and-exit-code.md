# 23 · 自然退出无人察觉（以及退出码）

承接 [22](22-status-detection-repair.md) 第 4 节留下的问题：`mark_exit` 没接线，因为拿不到退出码。

**结论：问题比 `mark_exit` 大得多。** 本轮先查清了它，然后一并修掉。

## 1. 先查清，不猜

`PtySession` 的文档早就写着：

> 读取线程阻塞在 `read()` 上，只有**关闭 PTY** 才会让它收到 EOF。

但**没有任何测试验证过「子进程自己退出」这条路径**——现有测试全都是**显式
`drop(session)`** 之后才等到通道关闭的，那证明的是「我们主动关」，不是「进程自己走」。

于是先写了一条诊断测试：**全程持有 `session`**（不 drop、不 kill、不 release），
让子进程跑完，看通道会不会关。

### 实测结果：不会

```
子进程自然退出后读取线程必须收到 EOF。收到 15 秒仍未关闭，输出为：
"\u{1b}[6n\u{1b}[?9001h…aivc-natural-exit\r\n"
```

输出已经拿到、进程早就跑完了，**15 秒后通道依然开着**。

## 2. 这导致的真实故障

`terminal:exit` 只在「我们主动关」时才发得出来。因此：

| 场景 | 修复前的行为 |
| --- | --- |
| 用户在系统终端里敲 `exit` | 标签**永远显示运行中**，直到手动关掉 |
| CLI 自己崩掉 / 正常结束 | 同上 |
| 退出码 | **没有任何人拿得到**（`PtySession::wait()` 在生产代码里从未被调用过） |

而且 `use-terminals.ts` 一直记着 `running` 这个状态，界面却从来没有显示过它——
它此前只被用来「不在运行时跳过 resize」。**记着而不显示，等于没记。**

## 3. 修法：收养任务

### 为什么不能靠读取线程

`read()` 收到 EOF 的唯一条件是**关闭 PTY 主句柄**，而句柄归 `PtySession` 所有。
所以「进程结束了」这件事必须由**另一条路**发现。

### 为什么不能靠阻塞 `wait()`

`wait()` 要 `&mut child`，而 child 在注册表里。把它挪出来做 `spawn_blocking` 会让
`PtySession` 失去 `kill()` / `Drop` 需要的句柄。

### 采用：轮询 `try_wait()`

`SessionRegistry::insert` 时起一个收养任务（每路终端一个）：

```
每 250 毫秒：
  会话还在吗？不在 → 收手（那一侧已经收过尾了）
  try_wait():
    Some(码) → ① 先记下退出码  ② 再 release() PTY  ③ 收手
    None     → 继续
    Err      → 收手（再轮询只是白跑）
```

**顺序不能反**：`release()` 会**立刻**让读取线程收到 EOF，泵随即就来取码。码必须先落地。

`try_wait()` 是非阻塞的，250 毫秒一次、每路终端一个任务，代价可以忽略。

### 退出码怎么到泵手上

**退出码不经过输出通道。** 读取线程只知道「通道关了」。所以注册表多了一张表：

- 收养任务在 `release()` **之前**把码写进 `exits`
- 泵在通道关闭**之后** `take_exit_code()` 取走（取走即清表）

`take_exit_code` 返回 `None` 表示**这不是「进程自己结束」**——用户主动关闭了终端。
`stop()` 会显式把可能已落地的码丢掉，避免「进程刚好自己结束」与「用户同时点关闭」
撞在一起时把一次正常关闭报成崩溃。

泵把 `None` 映射成 `mark_exit(0)`（正常结束、静默）。**这不是拿 0 糊弄**：
这里的 `None` 有确切含义，而主动关闭本就不该报「异常停止」。

## 4. 界面：让「已退出」看得见

标签上现在会显示 `系统终端（已退出）`。

这不是装饰——没有它，本轮修的东西**在界面上完全不可见**：修好了「事件会发出来」，
而用户看到的仍然是一个没有任何变化的标签。

## 5. 验证

### 特征测试：把平台事实钉住

`conpty_does_not_report_eof_when_the_child_exits_on_its_own`（`aivc-terminal`）

它记录的是**平台事实**而不是期望行为：直接驱动 `PtySession`、**不经过注册表**（因此
没有收养任务），断言「输出到了」+「通道没关」。这样收养任务存在的理由随时可查，
而且**如果哪天它开始失败，说明平台行为变了**，收养任务可以简化——注释里就是这么写的。

### 回归测试：自然退出必须走到前端

`a_natural_exit_reaches_the_frontend_with_its_code`（`aivc-ipc`）

**不 drop、不 stop、不 kill**，全指望收养任务。断言：泵能结束、恰好一条
`terminal:exit`、`terminalId` 正确、`exitCode == 0`。

**测试里要有人替 xterm.js 回答 ConPTY 的光标位置查询（DSR）** ——不回答的话 ConPTY
不推进会话，子进程也不会结束。这是第一次写这条测试时失败的原因。

### 假绿检查

去掉 `self.spawn_reaper(id)` 后重跑，测试红了，而且失败信息把病根展示得非常干净：

```
自然退出必须在超时前让泵结束；否则标签会永远显示运行中。已收到的输出：
[… {"data": […97, 105, 118, 99, 45, 114, 101, 97, 112, 45, 112, 114, 111, 98, 101, 13, 10]}]
```

最后一块数据就是 `aivc-reap-probe\r\n`——**输出全都到了，进程也结束了，通道就是不关**。

## 7. 顺带发现的两处工具问题

- **`ConPTY` 写进文档注释必须加反引号**：clippy 的 `doc_markdown` 会把它当成
  漏了反引号的标识符，`-D warnings` 下直接编译失败。同类的还有 `Windows`。
- **前端构建必须提权**：`vite`/`vitest` 在受限沙箱下加载配置失败（报错出现在
  `loadConfigFromFile`，看起来像配置写错了，其实是被沙箱拦了）。
  与 `cargo`、`ui-check.ps1` 一样，属于**已知需要更宽访问**的一类。
