## 0. 先说一件已完成的事：会话列表消失

**用户报的**：「点击进入终端会话后，列表内容就消失了」。

**根因（已修）**：`use-console.ts` 的 `openAt` **无条件**调用 `selectTarget(target.id)`，而它带
`setSessions([])` 副作用；列表重载 effect 只在 `[targetId, view, query]` 变化时重跑。
在当前目标下点会话 → `setTargetId(同一个值)`（无变化）+ `setSessions([])`（清了）
→ **没有任何东西把它填回来**。

**修法**：只在**真的换目标/平台**时才走 `selectTarget`；判据抽成纯函数 `planTargetSwitch`，
4 条单测覆盖（同目标 / 同平台换目标 / 跨平台 / 同编号跨平台）。

**截图对照**：`1-整体布局.png`、`9-进入终端会话.png` 都显示**侧栏与终端同时可见**——
旧平台从来不会因为「进了终端」就把列表收起来。

> **2.2 是用户明确点到的**（「终端下方自管输入」）。它是旧平台终端区最重的一个组件，
> 承担「不想在 TUI 里打字」这一条真实需求——长提示词、贴图片、拖文件都靠它。
>
> **已查清它的显示条件**（`embedded-terminal.tsx`）：
>
> - `const initialInputMode = sessionId ? "terminal" : "composer"`（L65）
> - `composerVisible` 初值 `= !sessionId`（L68/L83）
> - **`revealComposer()` 的触发点是「终端有第一段输出」**（L414-420）：
>   `if (!composerVisibleRef.current && data) { revealComposer(); scheduleFitTerminal(); }`
>
> 也就是说：**新会话一进去就有 composer；恢复历史会话时它先藏着，
> 等终端吐出第一段输出就自动出现。** 这个「自动出现」不是可有可无的细节——
> 少了它，恢复的会话里用户**永远看不到** composer（因为没有任何按钮能把它调出来，
> `revealComposer` 是唯一入口）。

### 11.8 5.6「平台 Base URL」：选了后端给字段，并挖出三处字段错位

**结论：选 B（后端给字段），而且它其实不是「二选一」—— A 在端口自动分配时做不到。**

三条依据都是读代码得到的：

1. **真实端口只有后端知道**。`server.rs` 是 `settings.port.saturating_add(offset)`，
   端口为 0 时 `TcpListener::bind` 交给操作系统选，只有 `listener.local_addr()` 知道结果。
   `activePort` 这个字段**在后端一次都没出现过**——界面无从拼出正确的 URL。
2. **那份 URL 已经存在，而且是注入给 CLI 的同一个字符串**。`server.rs` 拼出
   `http://{bound}` 存进 `state.set_address()`；`route.rs` 注入路由时读的就是它。
   界面另拼一份就可能「面板显示的地址 ≠ CLI 实际连的地址」——对 Base URL 来说，
   这两者不一致正是最坏的情况。
3. **拼法有第二份就会漂移**（前端此前已经在两处各拼了一遍）。

#### 顺带挖出的三处字段错位（都已修）

`get-port` / `set-port` / `set-enabled` **各返回各的**（`{port}`、`{port}`、`{enabled}`），
而前端把三者都声明成 `GatewayPortStatus`：

| 后果 | 实测证据 |
| --- | --- |
| 「配置端口」输入框里是**字符串 `"undefined"`**（`String(undefined)`） | 探针读到 `value=undefined` |
| 「当前端口」永远显示「未启动」 | `activePort > 0` 对 `undefined` 恒为假 |
| 状态栏/工作台的网关格**永远显示「未启用」**，即使网关开着 | `enabled` 恒为 `undefined`（假值） |
| 点一下「启用」就把另外两个字段抹掉 | `setStatus(返回值)` 只拿到 `{enabled}` |

最后一条最讽刺：`status-bar.tsx` 的注释专门写着「把『没取到』显示成『未启用』，
用户会去设置里找一个其实已经开着的网关」——**字段错位正好制造了它要避免的那个后果**。

测试全绿是因为它们注入的是自己编的假数据，形状由自己定；真实契约对不上时，
**测试反而证明了错误的东西**。

#### 改法

- 三条命令返回**同一个形状**：`{enabled, configuredPort, activePort, baseUrl}`；
- `baseUrl` 直接取 `state.address()`（注入给 CLI 的那个字符串）；
- `activePort` 从地址里解析（复用 `route::port_of`），空串即「没有在监听」；
- 前端把三处**手抄的子集类型**（`{enabled; activePort; configuredPort}`）换成真实类型——
  手抄的子集正是让这个错位躲过类型检查的原因；
- 状态栏与工作台共用一个判断函数，补上此前完全没被表达过的第四态
  **「已启用，未监听」**（端口被占、启动失败、还在启动中都会走到这里）；
- Base URL 旁边加「复制」，并按 `configuredPort` 是否为 0 提示
  「每次启动都可能不同」/「重启后地址不变」。

#### 关于「地址可达性」这条判据

我原本想让探针**往那个地址真的发一次请求**。实测发现 webview 有 CORS：
被拦时抛的也是 `Failed to fetch`，与「端口上没人监听」在 JS 里长得**一模一样**。
于是先做**对照实验**（拿一个几乎肯定没人监听的端口比），两者结果相同，
探针就如实报「**无法判定**」，而不是把探针的限制写成产品缺陷。

替代证据是结构性的：`baseUrl` 与 `activePort` 出自同一个字符串，而
`route.rs` 注入给 CLI 的读的也是它——「面板 ≠ 实际服务」在构造上不可能发生。

#### 判据

后端新增 4 条测试（含**三个命令的键必须完全一样**、`NaN`/畸形地址不 panic）；
前端新增 12 条（四种处境逐种钉死）；探针 `gateway-base-url.js` **12/12**。

#### 这一轮的一个操作教训

探针跑的是**嵌进二进制的界面**，不是实时读 `ui/dist`。我改完前端只跑了 `vite build`
就去探针，于是验的是「旧前端 + 新后端」——三个 Base URL 相关的断言全红，
而真实原因是我自己没重编。`app-probe.ps1` 里其实**自带这道守卫**
（`ui/dist` 比 exe 新就拒绝跑），但我那次 `dist` 是旧的、守卫放行了。
**改前端之后必须 `cargo build -p aivc-app` 才能真正验到。**
