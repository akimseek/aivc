## 上一轮为什么被否

第一轮的四套只画了「会话浏览器」——**那只是这个应用的一小部分**。

真实的功能面（从旧渲染层与 Rust 命令面盘出来的）：

| 模块 | 内容 |
| --- | --- |
| **sessions** | 列表（活跃/回收站/收藏）、消息分页、分支、复制、导出、重命名、批量操作 |
| **terminal** | 内嵌终端（xterm 接管 TUI）、系统终端、多标签、**终端关注中心**（等待确认时提示） |
| **vendors** | 供应商 CRUD、API Key、Base URL、模型、**路由与失败转移** |
| **gateway** | 端口、健康、请求日志、失败转移规则 |
| **skills** | 技能列表、导入 |
| **workbench** | token / 上下文占用 / 模型 / 供应商路由 |
| **settings** | WSL Codex 目录、工作区预设、CLI 环境 |
| 全局 | 菜单栏、命令面板 `⌘K`、状态栏、平台状态/诊断、CLI 安装器 |

以及真实的程序骨架：

```
菜单栏
└ main.app-shell
   ├ aside.sidebar    SidebarHeader（平台/目标/状态） + SidebarControls（视图切换/搜索/批量）
   │                  └ 互斥视图：工作台 | 快捷访问 | 全局搜索 | 会话列表
   └ section.workspace TerminalWorkspace（会话标签 + 内嵌终端 + 系统终端） + 覆盖层
   └ StatusBar
```

**结论**：布局不是「把会话列表和消息并排放」，而是要回答**七个模块怎么共存**。
这一轮的三套是对这个问题的三个不同答案。

## 两个与布局无关的待定问题

### 1. 框架选型

布局定了再定实现。我倾向 **React + TypeScript + Vite**（生态最全：终端有 xterm、
长列表有成熟虚拟化），但**结构会与旧工程完全不同**：单一 IPC 客户端、按功能切分、
设计令牌而不是一个八千行的 CSS 文件。选它是因为「可持续」，不是因为它原来是这个。

### 2. 一个真实的阻塞：新前端的依赖装不上

`npm install` 报 npm 内部错误 `Cannot read properties of null (reading 'edgesOut')`。
已排除权限问题（把缓存指到工作区内仍失败）与版本问题（都是镜像里有的版本）。

嫌疑最大的是那台机器的 npm 缓存**属于 node v20**（`D:\tools\nvm\nvm\v20.19.5\node_cache`），
而实际运行的是 v24。下一步会试 pnpm，或用全新缓存目录重装。

**这不影响看方案**，但必须在写真正的界面前解决。
